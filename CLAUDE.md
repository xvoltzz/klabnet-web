# klabnet-web: notes for Claude

klabnet is the klab.gg homelab's own app: chat (Matrix), feed, music (Navidrome), photos and home, as one site at `user.klab.gg`. Feed, Chat and Photos are one page, Social (see below). It's also the inside of **klabnet-desktop** (the Electron app for Windows, Linux and, in progress, macOS; see that repo's CLAUDE.md for the Mac work). The server side is **klabnet-api** (FastAPI + SQLite). README.md covers architecture and deployment.

## How the code is put together
- No build step. `index.html` loads `css/app.css` and `js/NN-*.js` as classic `<script defer>` files that share globals. Top-level `const`/`let` are global bindings but **not** `window` properties (e.g. `ND_URL`, `KLABNET_VERSION`). Later files wrap earlier functions by reassigning them (`openFS`, `updateQueueBadge`, `syncShuffleBtns`).
- **Every change to CSS/JS needs a version bump**: `KLABNET_VERSION` and every `?v=` in index.html (`sed -i 's/v2026\.MM\.DD\.N/v2026.MM.DD.N+1/g' index.html`), then `./check-version.sh`. The service worker serves `?v=` files cache-first, so a stale version means stale code. This applies to testing too.
- Icons are a subset font. Using a new `ti-*` icon means rebuilding it with `scripts/build-icons.py` (needs fonttools + brotli; check the result is LF, not CRLF).
- Syntax-check JS with `node --check js/<file>.js`.

## Deploying
- Four remotes: `origin` (Gitea), `github`, `staging` (→ staging.klab.gg) and `prod` (→ user.klab.gg). The last two are bare repos on 192.168.0.6 with a post-receive checkout.
- **Push only when the owner says so.** "push" means all four. "push to staging" means staging only. Verify afterwards, e.g. `ssh klab@192.168.0.6 'grep -o "v2026[.0-9]*" /home/klab/web/index.html | head -1'`.
- Commit as `xvoltzz <40217474+xvoltzz@users.noreply.github.com>`.
- **klabnet-api** is deployed by the owner (`git pull origin main && git push prod main` on the API host). Commit and push API changes to its Gitea/GitHub remotes, then tell them to deploy.
- Ask before touching the live Caddy config.
- **index.html gets cached** (2026-10-24): Caddy's file_server sends it with an ETag and no `Cache-Control`, so browsers and the apps may keep using their copy for hours after a deploy (heuristic freshness), old markup against the newer scripts the service worker hands out. That was "the feed doesn't show until Ctrl+Shift+R". The page now checks at start (`checkForUpdate(true)` in js/06-prefs.js, `cache: 'no-cache'`) and reloads itself once onto the new version. The real fix is `Cache-Control: no-cache` on `/` and `*.html` in Caddy, suggested to the owner (theirs to change). The other half (same day): a page loaded mid-deploy asked for `?v=NEW` before the new file was up and got the old one, which the service worker then kept under the new name forever, so Ctrl+Shift+R (which skips the worker) fixed it once and a plain reload broke it again. sw.js now re-checks each `?v=` file against the server once per worker in the background, replaces a wrong copy and tells the page to reload (`klabAssetStale`). Deploy the JS/CSS files before index.html all the same.

## Design rules (the owner cares a lot about consistency)
- **Music is the reference.** It uses:
  - a sidebar with 38px rows, section labels (10px semibold tracked caps, dim), and a big 30px bold view title with a dim count beside it
  - panels with a hairline border, radius 10px and a glass fill
  - two kinds of button: primary (filled with the text colour) and secondary (glass with a hairline)

  Photos, the full-screen player and the chat search were all redesigned to match it. Anything new should look like it belongs in Music.
- Sentence case for everything you press or read; caps only for section labels.
- Boxy (radius 6 to 10px), blur/glass, a soft "bloom" glow on lit things.
- Pointer cursor on buttons. No text selection except in inputs (it's an app, not a document).
- No phone UI on a desktop: the phone layout is only for `(max-width: 760px) and (pointer: coarse)`, and narrow desktop windows keep the desktop layout.
- In the desktop app, Windows and the Mac look native: Windows (WinUI title bar, Acrylic, NavigationView sidebar) and macOS ("KLABNET FOR MAC" in css/app.css). These are keyed off `html.klabnet-app` and `data-platform`/`data-desktop`.
- **Linux has a look of its own** ("KLABNET FOR LINUX" at the end of css/app.css, `data-desktop="linux"`, from the native app klabnet-kde): the owner found the Breeze look ugly and wanted one klabnet look for Plasma, GNOME and Hyprland, cleaner, borrowing from the other apps without straying far. klabnet's header is the title bar with klabnet's own window buttons; the sidebar is the window's glass and the page a deeper sheet beside it; the selection is the accent, filled. The app draws the window's rounded corners and rim itself (`html.app-round`, `--win-r`), so don't add those here. Since klabnet-desktop 1.3.0 (2026-10-24) that app is the Electron one again (QtWebEngine only drew at 60fps): it gives klabnet the same bridge (`shell: 'kde'`, its preload.js draws the frame), so this CSS is unchanged. The older GNOME (libadwaita) and KDE (Breeze) skins were for klabnet-desktop's Linux builds before 1.3.0.
- Scrollbars are hidden everywhere.

## Voice (built 2026-10-06; not yet run against the real homelab)
Drop-in voice channels, like Mumble's or Discord's, on a self-hosted **LiveKit** server (WebRTC). The owner wanted "self-hosted, low-latency voice" and first thought of Mumble; a browser can't speak Mumble's protocol, LiveKit's client is the same JavaScript in a browser and in the apps.
- **Where things are:**
  - `js/22-voice.js`: all of it. The channels are a group in Social's sidebar (`#socVoice`: the channels as rows you press to join, the people in each, and mute / deafen / leave while you're in one; owner's ask, 2026-10-24, replacing the header's headset button and its panel). `#voiceMicBtn` shows only while you're in a channel, on every page: at the foot of the sidebar (above the player; js/07-tabnav.js `place()` moves it) with the channel's name, its mic lit green while you talk (`.speaking`) and red when muted, growing in and shrinking out (`.tucked`); in the header when the tabs are on top. Pressing it mutes. Settings → Voice has the devices, open mic or push to talk, and the processing switches.
  - `js/vendor/livekit-client.umd.js` (600KB) is fetched the first time someone joins, not at load. Its `?v=` is the library's version, not `KLABNET_VERSION`.
  - **klabnet-api** `app/routers/voice.py`: channel names (SQLite), who's in each (asked of LiveKit, cached 2s) and the join token. LiveKit itself is the `livekit` service in klabnet-api's `compose.yml`. Its README's "Voice" section is the setup (DNS, Caddy, router ports, `.env`).
- **It hides itself** until `GET /api/voice` says `enabled: true`, so the site is the same as before wherever LiveKit isn't set up. Caddy only forwards a fixed list of `/api` prefixes: `/api/voice*` has to be on it.
- **Identity is the klabnet username**, one per person: joining on a second device takes over from the first ("Voice moved to your other device").
- **Muted and deafened are participant attributes** (`mute`, `deaf`), not the track's mute bit, because a push-to-talk microphone is muted between words without its owner being muted. The API reads the same attributes for people outside the channel.
- **Going quiet cuts the microphone at the source first** (`mediaStreamTrack.enabled = false` in `applyMic`), then tells LiveKit. Keep it that way: a mute that fails must never leave a microphone open.
- Per-device settings are in `localStorage` under `klabnet_voice` (not synced prefs: device ids mean nothing on another machine).
- `window.klabVoice` (`join`, `leave`, `toggleMute`, `toggleDeafen`, `state()`) is there for the desktop apps and for tests.
- **Testing it locally:** LiveKit is one binary (`livekit-server --dev --node-ip <WSL address>`, key `devkey` / secret `secret`); run the API from AGENTS.md's rig with `LIVEKIT_URL=ws://localhost:7880 LIVEKIT_API_KEY=devkey LIVEKIT_API_SECRET=secret`. Headless Chrome with `--use-fake-device-for-media-stream --use-fake-ui-for-media-stream --autoplay-policy=no-user-gesture-required` gives each tab a microphone; `--use-file-for-fake-audio-capture=<wav>` with something speech-like is needed for the speaking rings (the default beep is too short for LiveKit to call it speech). Two tabs as two users covered joining, hearing each other, mute, deafen, volume, push to talk, switching, a deleted channel and the second-device takeover.
- **Not done yet:**
  - Phones: the buttons are hidden under the phone media query. It needs its own layout.
  - The desktop apps: a global mute / push-to-talk key (a page only sees keys while it's focused), tray and Dock items. See klabnet-desktop's CLAUDE.md.
  - Nothing shows who's in voice outside Social's sidebar (presence cards).

## Playlists (built 2026-10-08; not yet run against the real homelab)
A playlist has a name, a description, a cover, a color and its songs, and lives on **klabnet-api** so other people can see it. They used to be a name and some songs in each person's prefs.
- **Where things are:**
  - `js/09b-playlists.js`: all of it (the store, the sidebar rows, the page, the editor, Add to playlist, the right-click menu, Browse → Playlists, Home's card).
  - **klabnet-api** `app/routers/playlists.py`, under `/api/music-requests/playlists` so it rides a prefix Caddy already forwards. Covers are files on the media share (`playlists/<id[:2]>/<id>-l.jpg` 1000px, `-s.jpg` 300px); a new upload is a new id, so they're served as immutable.
- **Private, featured, open.** A playlist is private until its owner features it. A featured one is on Home's "Featured playlists" shelf and in Browse → Playlists for everyone; anyone can play it or save it to their sidebar. "Let others add songs" (`collab`) only works on a featured one: others add, and can take back what they added; only the owner (or an admin) reorders, removes, edits or deletes. Unfeaturing takes it out of the sidebars of people who saved it.
- **The list holds summaries, not songs** (`_pls`: count, length, the first four album covers). A playlist's songs are fetched when it's opened or played (`plGet`). The list is cached in `localStorage` under `klabnet_pl_cache` so the sidebar is there at once, and refreshed when Music opens.
- **Its page is the album page's panel.** `window.klabApPage.open()` in `js/13-tail.js` lets another file put a page in `#apPanel` with the same Back, stack and blurred backdrop; `openPlaylistPage(id, name)` uses it, and `js/17-history.js` wraps it like `openAlbumPage`. While it's open its sidebar row is the lit one (`setNavRow`), and the section underneath gets the highlight back after.
- **Covers:** an uploaded picture goes through the square cropper (`openImageCropper`, `shape: 'square'`); "Make one" draws an emoji or a few letters on the playlist's color (`plDrawCover`) and uploads that as a picture. With no cover it shows the first four album covers as a 2x2 (`plArt`).
- **Two things to keep working:**
  - *The old list.* `klabnet_playlists` (still a synced pref) is handed to `POST …/import` the first time this runs against an API with playlists, then emptied. The API remembers every old id it has taken (`playlist_imports`), so a second device holding the same list doesn't make copies and a deleted one doesn't come back.
  - *An API without playlists* (the site is deployed separately from the API): the list answers 404 or 405, `_plServer` is `false`, and everything works on the prefs list as before, with just a name. Every store function (`plCreate`, `plAddSongs`, …) has that branch.
- `tests/playlists.mjs` runs all of it against the local rig (two users through the `x-dev-user` header). It doesn't play anything.
- **Not done yet:**
  - Reordering on a phone: it's drag and drop, which touch screens don't do.
  - Sharing a playlist to the feed or chat, and showing someone's playlists on their profile.
  - An open playlist doesn't update live while you look at it; it's refetched when the list next refreshes.

## One player on every device (built 2026-10-12; not yet run against the real homelab)
Like Spotify: of everywhere you have klabnet open, one device makes the sound (the *active* one) and the rest show the same song, position, queue and Up next, and work as its remote. "Play here" (the Devices button in the dock and the full player) moves the sound. It replaced every tab playing its own thing, and with that a presence card that flipped between them.
- **Where things are:**
  - `js/23-session.js`: all of it. It loads last and wraps `playSong`, `nextSong`, `prevSong` and `updateQueueBadge`.
  - **klabnet-api** `app/routers/session.py`, under `/api/music-requests/session` so it rides a prefix Caddy already forwards. Each page holds a stream open (`…/stream`, server-sent events). The active device reports what it's playing (`PUT …/state`); the others send their button presses (`POST …/cmd`) for the API to hand on. All of it is in the API's memory: one uvicorn process, nothing stored, and after a restart the active device says it all again.
- **A remote doesn't play, it stands in.** The site reads and drives `playerState.audio` in a couple of hundred places. Rather than teach each one about remotes, 23-session.js makes that one element stand in for the active device's while this one is a remote (`mirror`): `currentTime`, `duration`, `paused`, `volume`, `muted` and `loop` are own properties on it that answer with the active device's, `play()`, `pause()` and seeking become commands, and `play`/`pause`/`timeupdate`/`seeked`/`loadedmetadata`/`loadstart`/`volumechange` are fired by hand as the news arrives. So code that uses the audio element just works on a remote. Code that must only run where the sound is checks `window.klabSession?.mirror` (the scrobble does).
- **Commands** (`POST …/cmd`, `onCommand` in 23-session.js): `play`, `resume`, `pause`, `seek`, `next`, `prev`, `queue`, `set` (volume, mute, shuffle, repeat), `take` ("you play it") and `no` ("I couldn't"). `list` replaces what's lined up (the list, where it's at, the queue) without restarting the song: the site never sends it, the phone apps do, since they keep what's coming as one list.
- **`playSong` asks first.** After setting the song and the dock, the base `playSong` (js/02-player.js) calls `klabSession.mirrorPlay(song)`; true means another device has it. A song picked on a remote goes to the active device with the list, index and queue if they changed.
- **Roles:** `off` (no API for it: exactly as before), `idle` (nobody is playing), `active`, `remote`. Idle with nothing of its own loaded, a device is *parked* on whatever was last playing anywhere, paused where it stopped; Play carries on from there, on that device.
- **Who is active:** playing where nobody is makes you it. Otherwise only "Play here" (or being picked in another device's Devices menu) does: picking a song on a remote plays it on the active device. The API lets go of an active device 10 seconds after its stream drops, or after 10 minutes paused, so Play on your phone doesn't start the PC in another room.
- **Positions are on the API's clock:** "this far in, as of then". Each device works out its offset from that clock from the messages it gets. Remotes count forward from the last report; the active device reports on every change and every 10 seconds.
- **What you ask for shows at once** (`expect()`), and news that doesn't match it is held for a moment, since it's older than the asking.
- **Presence:** every beat carries `device` (`KLAB_DEVICE`, a new id per page load) and `remote`. The API keeps the latest beat per device and writes the card from the one that's really playing (`_shown` in routers/presence.py). `DELETE /api/presence?device=` (the phone apps send it when put away with nothing playing) takes away only that device, so a card showing another one stays. Builds of the phone apps from before this send no `device` and count together as one.
- **Volume** on a remote is the active device's. Each device keeps its own, and gets it back when it plays.
- **Listening parties** are heard on the device they're joined on (joining brings the sound there), and moving your music to another device leaves one you were following.
- A login song doesn't play if another of your devices is already playing.
- `window.klabSession` (`role`, `remote`, `mirror`, `ready`, `playHere()`, `moveTo(id)`, `state()`) is there for the desktop apps and for tests.
- **The phone apps have their own end of it** (built 2026-10-12; compiled, not yet run on a phone): `Core/PlaySession.swift` in klabnet-ios and `core/PlaySession.kt` in klabnet-android, the same roles and messages as 23-session.js. Their `Player` is the stand-in there: while `mirror` is on it shows the other device's song and lists, and its buttons are sent.
  - *They keep what's coming as one list* (played, current, up next), where the site has a list, a place in it and a separate queue. Reporting, an app sends the list whole with the hand-queued songs at the front of up next as the session's queue (`handQueued`). As a remote it sends the whole order back with `list`, and `play` with the list when it has changed.
  - *Shuffle and repeat.* An app has no shuffle switch (it shuffles what's coming, once), so a remote's shuffle does that, and a song picked on a phone turns the site's shuffle off. The session's repeat is "this song again"; an app's "repeat all" stays on that phone.
  - *Put away.* iOS stops an app that's off the screen and silent, so the iPhone leaves the session then, and one that was playing and is paused lets go after 20 seconds: Play on another device then plays there. Android keeps a paused player alive for ten minutes (Media3's own grace), which is as long as the API keeps a paused device. Either rejoins and takes the music back when Play is pressed on it (the lock screen, headphones).
  - *Not there:* lock-screen controls for music playing on another device, starting a phone that's been put away (both would need push notifications), and CarPlay or Android Auto while the phone is a remote.
- `tests/session.mjs` runs all of it with made-up songs and several windows as one person. Navidrome is never asked to play anything.
- **Not done yet:**
  - The session isn't stored: an API restart with nothing playing forgets what was last played.
  - A browser tab that's in the background and has never played anything can't be started from another device (Chrome doesn't load audio there until it's shown; the desktop app isn't affected). The device that asked is told to press Play there.
  - Devices of the same kind have the same name ("Chrome on Windows" twice). The desktop apps could send the computer's name.
  - A list longer than 2,000 songs is sent as the 2,000 around where it's at.
  - Two devices can't both play on purpose (a second room). Starting one stops the other.

On a narrow touch screen they go back to the action bar beside the photo.

- **Feed's first load runs even while the page is hidden** (`fetchFeedPage` in js/12-feed.js; the hidden guard applies only once the feed has loaded). klabnet-desktop builds its window with `show: false`, so every launch, and the relaunch after an update, started hidden: the first fetch was skipped and Feed stayed blank until a visibilitychange that Wayland doesn't always send, or the 30s poll. Arriving on Feed also fetches if it never loaded (`klabFeedShown`).
- **Feed invisible but clickable, until a reload (the real cause, found 2026-10-31).** The old section scroll reveal (js/13-tail.js, `body.sec-reveal .sec`) hid every `.sec` at opacity 0 until an IntersectionObserver saw 6% of it. Since Feed scrolls inside a window-high panel, its section (~19,000px with 50 posts) could never show 6%, so it was never revealed. It only appeared when a reload caught it still short (before pictures loaded). The reveal is gone; tab panels fade in on their own. Don't hide content behind an observer threshold again: a tall enough element never reaches it.
- **Feed's requests have a deadline that covers the body** (`getPostsJSON`, 15s, 2026-10-31). `fetchTimeout` stops its clock when the headers arrive, so a response that stalled halfway left `r.json()` waiting forever with `_feedPending` set. Every later poll, visibilitychange and visit to Feed then returned at once, and Feed sat on "Loading feed…" in the browser and every app until a reload. Reproduced with a proxy that sends the headers and never the body. Many other `await r.json()` calls after `fetchTimeout` have the same gap.
- **Social's home** (js/25-social.js): Music Home's head, the newest photo uploads as a moving collage (the owner said it can't be Cover Flow, it's "gotta be more photography oriented"): `.soc-collage` of `.soc-tile`s, `pack()` lays out a hero column on alternating sides plus justified rows, and every 9s `drift()` trades one shown photo for one not shown (or two shown ones) and the tiles glide there over 1.8s with no overshoot; only every sixth tick, or ←/→, is `shuffle()`, the whole wall reordering with the hero to the other side. The owner found 4.6s whole-wall shuffles "nervewracking", so keep it calm. It pauses on hover/focus, out of view, hidden, or with reduced motion; ←/→ shuffle by hand; a tile opens the photo in Photos. Then the latest posts (12) as cards. On a big screen the posts fill the height left under the photos (`fit()` picks 1–3 rows of at least 210px, sets `--rows`/`--lines`, and adds `.tall`, where a card shows its picture via `klabFeedImage` or its song's cover). The posts are Feed's own (`klabFeedPosts`, and it listens in on `klabHomeFeedChanged`); only the photos are fetched, and only while it's showing.
- **Phones** (and Photos on a narrow touch screen): the four are chips along the top, as Music's sidebar is there, and Chat's list is the Chat page's first screen (`chat-rooms-view`), with the search box.
- **Social's rows are `.picker-tab`s too** (for Music's look), with `data-soc` instead of `data-tab`. Music's code must match `.picker-tab[data-tab]` only: matching every `.picker-tab` made a click on Feed play Music's nav sound on top of its own, load a Music section called `undefined` ("No tracks found") and push a Music step onto Back.
- **The header's sidebar button** hides Social's sidebar as one (`pane-off-social`); the old `pane-off-chat`/`-photos` are gone.
- **Not done yet:** recent chat on Social's home, and a phone run on a real device.


## Music's Activity page

The owner asked for it to make up for the presence cards being gone: "last thing each person listened to and where they're at live if they're listening... total listen time, basic stats. favorite artist".
- **Where:** Music's sidebar, under Home (`data-tab="activity"`), js/27-activity.js with its own `loadPickerTab` wrapper (the outermost one, so it does what the layers under it would on the way to a view they don't own: `klabBrowse.leave()`, the songs observer, the sort button). The CSS block "Music's Activity page" is at the end of css/app.css.
- **Data:** klabnet-api's `GET /api/music-requests/activity?tz=` (app/routers/listens.py). Plays are counted server-side from presence's beats, only the beat of the device someone's card shows, into the `listens` table; plays under 30s aren't counted. The beat sends `position`, `duration`, `album` and `coverArt` for it (`postPresence` in js/11-presence.js, plus a beat after `seeked`). Counting starts when that API is deployed, so the numbers start at zero. Under `/api/music-requests/` because Caddy only forwards known prefixes. An API without it answers 405, which reads as "Activity needs the latest klabnet-api".
- **Live:** polled every 10s while showing (stops off the view or off Music, via `klabMusicTabChanged` in js/07-tabnav.js). The bars of what's playing tick every second from the last poll (`posNow`) without redrawing the page.

## Things built recently (Sep 2026) that are easy to trip over
- **High-res album art** (display only; Navidrome's own art is never changed):
  - `klabHiResArt()` in `js/09-music-extras.js` calls the API's `/api/music-requests/artwork` (iTunes → Deezer → Cover Art Archive, strict matching).
  - The API keeps the images on the media share and serves them from `/api/music-requests/artwork/files/<id>-l|-f`.
  - It's used by Cover Flow (`hires` option of `makeCoverFlow` in `js/15-music-home.js`), the full-screen player and the cover viewer.
  - Browsers remember lookups in `localStorage` under `klabnet_hires_art2`.
- **Cover Flow performance:** `-webkit-box-reflect: none` is *invalid* in Chrome (use `initial`). The reflections are real `.mh-refl` images now, because box-reflect redrew every frame and was ~15x slower at 4K.
- **Photos:**
  - On desktop, `js/14-photos.js` moves its controls into the sidebar (`placeChrome()`). On touch screens ≤900px it puts them back beside the photo.
  - The photo count comes from the API's `total` on the first page.
  - The slideshow (`js/19-slideshow.js`, the S key or the Slideshow button in Photos' head) works through `window.klabPhotos`, which 14-photos.js exposes (items, urls, paging, the photo's song). It holds only two photos at a time, loads older pages in the background, and keeps the screen awake with a Wake Lock.
- **Memory:** klabnet sat near 1GB in the desktop app. The details, measurements and the desktop-side fix are in klabnet-desktop's CLAUDE.md ("Memory (RAM) and GPU"). The rules this repo follows because of it:
  - Blurred backdrops never need big art: `klabSoften` (js/00-util.js) bakes them to 96px and downsizes any `getCoverArt` source to 300px before it's fetched. Don't give a blurred background a screen-sized image.
  - Decoded pictures are the memory. Chromium keeps every one it has drawn until the OS says memory is short. When a screen lets go of many big pictures, call `window.klabnetDesktop?.trimMemory?.()`, as Photos does when you leave it and the image viewer does when it closes.
  - Photos keeps at most 6 preloaded photos (`preloaded` in js/14-photos.js) and clears them on leaving the tab.
  - Animations that never stop make the window redraw every frame (steady GPU at 4K behind Acrylic), so avoid adding new ones. The ones there are (the sidebar visualiser, the listening ring, the prompt cursor, the EQ bars) pause while the window lacks focus: `html.win-idle` from js/16-motion.js, "WINDOW IDLE" at the end of css/app.css. A new looping one goes in that list.
- **Away** (js/11-presence.js + klabnet-api routers/presence.py): each presence beat sends `activeAgo` (seconds since this device was used), `idleKnown` (it sees the whole computer: the apps' `klabnetDesktop.idle()`, or Chrome's IdleDetector once allowed in Settings -> Away status) and `lockedFor`. The API marks someone away after 5 minutes with nothing used on any device, or on a locked screen. Other browsers only see klabnet's own input, so they never make anyone away.
- **Prefs** save with `PATCH /api/prefs` (just the changed fields, merged on the server, one request, so it survives a closing tab), falling back to GET+PUT on an API without PATCH.
- **Favourites** are slimmed song records (`slimSong` in js/05-favorites.js), up to 2000; adding past that says so rather than dropping the oldest.

## Radio

The owner wants, long term, "a gta v like radio system where anyone can tune in at any point in the day and theres a cool picker. everyone will build their stations as one big audio file & they just loop and loop. but EVERYONE is synced up".
- **Live, no longer experimental:** Music → Radio (right under Home in Music's sidebar, `pickerTab` 'radio') lists the stations; the dock is the tuner, and the Q wheel stays for quick jumps. The Settings → Experimental switch and `_settings.radio` are gone.
- **The tuner is the dock** (owner's ask, 2026-10-27: "the scrubbing … within the player bar, no separate floating bar"). Whatever tunes in (the Radio page, the wheel, a card, Activity) switches the dock to its radio mode, and there's no other dial and no pill over the dock any more. The FM band (87.5–108) scrolls sideways under a fixed needle: scroll it, use an up-and-down wheel, drag it with a mouse, or swipe. Let go within 0.3 MHz of a station and it snaps on; elsewhere onto the nearest 0.1. Picking a station from a list (`tuneTo`) sends the needle sweeping across the band to it, static and all. Keys on the Radio page (capture phase, ahead of the player's own ←/→/Space): ←/→ ±0.1 (Shift ±1, and these don't snap onto a station), Page Up/Down the previous/next station, Space power. The dial's place is kept in localStorage `klabnet_radio_freq`.
- **Music → Radio** (js/28-radio.js `page`, "Music → Radio" in css/app.css) is a list, not a tuner: on top a dark display of what's on the needle (DSEG7 readout, signal meter, an On air / Tuning / Static / Off lamp, art, track, power and prev/next), following the dock's dial live; then the stations (frequency, art, what's on, On air, faces of who's tuned in), who's tuned in to the station on the needle, about it, and that station's chat.
- **The tracklist is a surprise** (owner's ask, 2026-10-27): a song is only ever shown while it's on (the display, the dock, the rows, the wheel, presence). No tracklist, nothing played or coming, no count down, nothing in the chat. klabnet-api sends a listener only the cue that's on and when it ends, as a cue with no name (`_on_now` in routers/radio.py); `trackAt` asks again once that passes. Only the station's editors get the whole list, for the form. Static between stations keeps showing the last station that came in. Three columns, two then one as it narrows (a container query on `.rd-page`).
- **Radio chat:** per station, klabnet-api `GET/POST …/radio/<id>/chat` (`after=` the last id; table `radio_chat`, the newest 300 kept, deleted with the station). Polled every 3s while the page shows; an API without it says so in the chat box.
- **The dock's radio mode:** the dock's radio button (`#dockRadio`) flips the dock between the player and the radio (js/28-radio.js `dock`; `.player-dock.radio-mode`, kept in localStorage `klabnet_dock_radio`). It shows the station's art (opens Music → Radio), a DSEG7 readout with a 5-bar signal meter, name and track, prev / power / next and the dial (60px per MHz). As the dock narrows, the readout goes first (the frequency moves in front of the name), then the name, then prev/next; the dial keeps its room. Switching to it turns the radio on; switching back, or playing music, turns it off and gives the dock back. Power off leaves it in radio mode. After a reload it comes back in radio mode but quiet. Tucked into the sidebar's visualiser (off Music on a computer) the dial counts as gone (`dockWanted()`): static stops, and a station only half in turns off.
- **The sidebar's visualiser** (`#dockPeek`) moves while the radio's playing too (`body.radio-on`, set by `paintPeek()`; `is-playing` stays music's, since the accent colour follows it) and its label says `98.7 · Station`; js/02-player.js's title sync stands aside while the radio's on.
- **One needle:** `makeDial()` builds a dial (only the dock's now); `needleAt()` moves every showing dial, the readouts (the dock's and the Radio page's display) and the sound. A dial that's following another one ignores its own scroll event (`expect`), so they don't fight.
- **Signal:** a station's level is 1 within 0.05 MHz, 0 past 0.25, eased between. Its volume is the dock's × that level, and looping band-passed noise (Web Audio) fills the rest while the radio's on. Coming onto a station tunes in after 180ms; a station lost to static is dropped after 1.2s. When the dial goes out of sight: a station coming in (level ≥ 0.5) plays on at full; anything else turns off. The static only plays while the dock's dial is showing and the tab is visible.
- **Frequencies:** every station has one (required when making it; the form suggests a free one), 87.5–108, at least 0.5 MHz from any other (409 "too close to …"). Stations from before got 88.1, 90.1, … by a one-time migration in klabnet-api's init_db. The wheel, the dock and the lists show it.
- **Authors:** a station can be uploaded for someone else: "By" in the form (`author`, offered from `klabPeople`). It's shown instead of the uploader everywhere, and when it's someone's username they can edit it too. Blank means the uploader.
- **Sync, with no streaming:** a station is one long file with a start time (`epoch`). Where it's at is `(now − epoch) mod duration` on klabnet-api's clock. js/28-radio.js asks `…/radio/time` four times and keeps the quickest (half its round trip is the lag), and every second checks its place. Within 60ms it leaves it, under 0.8s it plays up to 3% faster or slower to catch up, and past that it jumps. Two pages measured within ~10ms of each other once settled. It re-syncs on coming back to the tab and every 10 minutes when tuning.
  - *Phones looped back to 0:00* (fixed 2026-10-27). Keep these: a new file starts from its URL (`#t=<seconds>`), not a seek before `play()` (which phones drop); `play()` isn't held up by the clock sync (a phone only allows it close to the tap); positions are scaled by `stretch`, the browser's length over ours (a phone estimates a long VBR mp3's length from its size, and seeking past that estimate hit the end and looped to the start); `seekTo` never goes past the browser's end; a jump waits out `waiting`; and three jumps that don't land stop the jumping for a minute (`misses`, `calmUntil`) so it plays on instead of restarting. Not run on a real phone yet.
- **The wheel** (GTA's): hold Q, point, let go; or tap Q / the dock's radio button and click. Arrows, W/S/A/D, the scroll wheel and Enter work in it, and Esc closes it. The first slot is Radio off. The hub shows the station, what's on from its tracklist, who's tuned in (presence's beat carries `radio`), and a ring for where it is in its loop. A burst of static plays between stations when sounds are on.
- **Playing music turns the radio off, and tuning in pauses the music.** Not a remote's made-up `play` events (js/23-session.js), only music starting here. Volume follows the dock's.
- **Your stations** (from the tuner or the wheel; Edit station opens it at the one on the dial): upload a mix (mp3, m4a, aac, ogg, opus, flac, wav or webm; up to `RADIO_MAX_MB`, 1500 by default), a name, colour, description, an optional square cover (playlists' cover pipeline) and an optional tracklist (`0:00 Artist – Title` a line). Uploads go by XHR for a progress bar. Anyone can make one; the uploader, the author or an admin edits or deletes it. Replacing the mix keeps the start time.
- **klabnet-api** `app/routers/radio.py`, under `/api/music-requests/radio` (a prefix Caddy forwards). Files are `radio/<id>.<ext>` on the media share, a new id per upload, served immutable. Lengths come from mutagen (new in requirements.txt). An API without it: the wheel says it needs the latest klabnet-api.
- **Presence and Activity:** tuned in, the beat says the station instead of the song left paused: `song` is its current track (or its name), `artist` is `Name · 98.7 FM`, no `songId`, `playing` true (so listens don't count it). klabnet-api's presence GET adds `radio` (the station id) per listener, from the in-memory beats, and `live()` returns `radio` (routers/radio.py `now_on`: name, frequency, colour, cover, author, current track). Social's cards then show it and clicking one tunes in with them (`data-radio`), and Activity shows an "On the radio" card with Tune in.
- **Not done yet:** the radio in the full player and in the OS's media controls, Activity counting radio time (it shows who's on the radio, but listens only count songs), and a run on a real phone.
